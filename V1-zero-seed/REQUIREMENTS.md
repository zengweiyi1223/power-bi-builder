# Power BI Builder — V1 Zero Seed 需求与验收基线

## 1. 文档定位

本文定义 V1 零种子实验的范围、约束、证据和结论规则。当前状态为规划基线；未经明确指令，不启动 Power BI Desktop，不创建正式运行项目。

V0 是已完成且冻结的参照，不修改其需求、种子、运行产物或成功口径。

## 2. 唯一实验问题

从经证明为空的目录开始，仅由 Codex 生成 PBIP 入口、PBIR 报表和 TMDL 语义模型工程结构，Power BI Desktop 是否能够：

1. 直接打开该项目；
2. 不经人工创建新项目或“另存为”替换项目壳；
3. 显式保存并关闭；
4. 从磁盘重新打开；
5. 保持 Report 与 SemanticModel 的引用、最小页面和模型均可识别。

V1 不重复证明 V0 的完整业务报表功能，不同时扩展 Service 发布、多页面、新数据源或复杂视觉对象。

## 3. 术语

- **种子**：由 Desktop 或其他既有项目产生、随后被复制或改名使用的 PBIP/PBIR/TMDL 工程壳。
- **空目录**：在 Codex 首次写入前递归文件数和子目录数均为 0 的 `project/`。
- **Codex 生成态**：Codex 写入完成、Desktop 尚未打开时的磁盘状态。
- **Desktop 首开态**：Desktop 首次打开项目后、用户尚未保存时的状态。
- **Desktop 首存态**：用户首次显式保存并关闭后的状态。
- **稳定重开态**：从首存态重新打开后，无阻塞错误且项目对象可再次识别的状态。
- **结构性补写**：Desktop 新增或实质修复项目入口、Report/SemanticModel 引用、PBIR 根定义、页面、TMDL 根定义等项目成立所必需的内容。
- **非结构性规范化**：属性排序、缩进、换行、默认空属性、版本升级或等价序列化等不改变项目可识别结构和业务语义的重写。

## 4. 不变量与禁止项

- 不读取、复制或改名使用 `V0/seed/**`。
- 不把 `V0/runs/**/project/**` 或其他既有 PBIP/PBIR/TMDL 工程当作模板或实现参考。
- 不通过 Desktop 人工创建空白 PBIP、复制现有 PBIX/PBIP、执行“另存为”来补造项目壳。
- 不在一次失败试验的同一 `project/` 中反复覆盖后宣称成功；修复后必须使用新的 attempt 目录，并保留原失败现场。
- 不在首次打开前启动 Desktop 或 Modeling MCP 对目标项目进行写入。
- 不把 `.pbi/` 缓存、本机设置、自动恢复文件或临时文件当作正式项目组成。
- 不因 V1 需要而修改 V0 文件。

允许的来源包括本 V1 需求、微软公开 PBIP/PBIR/TMDL 文档与 Schema、V0 文档中的已记录事实、`V0/data/sales.csv` 和独立验证脚本。所有实际来源必须记入运行记录。

## 5. 最小生成物契约

Codex 在首次 Desktop 打开前必须生成一个名称自洽的项目，至少包含：

- 一个根 `*.pbip` 入口；
- 一个同项目命名约定一致的 `*.Report/`；
- Report 到 SemanticModel 的相对 `byPath` 引用；
- PBIR `definition/` 根文件和唯一空白 `Overview` 页面；
- 一个同项目命名约定一致的 `*.SemanticModel/`；
- `definition.pbism` 及可被 TMDL 解析的最小模型定义；
- 支撑目标 Desktop 版本打开所需、且能由公开规范合理推出的其他文件。

首次打开前不要求业务表、V0 的五个度量值或六个视觉对象。这样可把工程壳兼容性与 MCP 建模、数据刷新和报表设计解耦。

## 6. 重复实验矩阵

至少执行两组相互独立的正式试验：

| 试验 | 项目名 | 项目路径特征 | 目的 |
| --- | --- | --- | --- |
| A | `ZeroSeedAlpha` | 仓库内短路径，仅 ASCII、无空格 | 建立最小兼容基线。 |
| B | `零种子 Beta` | 不同父目录，名称和路径同时包含空格与 Unicode | 排除名称、编码和相对路径上的偶然成功。 |

每组必须从各自空目录独立生成，使用不同的项目标识符和页面标识符；不得复制 A 后改名得到 B。若目标版本已知不支持某类名称，仍应记录为路径兼容性限制，并增加另一组受支持但不同名称/路径的重复试验，不能静默降低重复性要求。

## 7. 操作职责与独立记录

### 人工操作

仅记录用户或执行者在 UI 中完成的动作，包括打开指定 `.pbip`、处理系统/隐私/预览确认、点击保存、关闭、重开和观察到的提示。写入 `logs/HUMAN_ACTIONS.md`。

### MCP 操作

记录 Modeling MCP 的工具名、目标连接、输入摘要、确认、结果和证据文件。写入 `logs/MCP_ACTIONS.jsonl`。MCP 在首次打开前不得对目标项目写入；首次打开后的只读回读可作为辅助证据。

### Codex 文件操作

记录 Codex 对目标运行目录的创建、修改、删除、哈希和理由，包括来源声明。写入 `logs/CODEX_FILE_ACTIONS.jsonl`。Desktop 启动后，Codex 不得把 Desktop 的写入冒充为自己的生成物。

三类记录不可合并成一个模糊的时间线；`VALIDATION.md` 只汇总并引用它们。

## 8. 首次打开前证据闸门

每个试验在打开 Desktop 前必须具备：

- 空目录证据：创建后、Codex 写入前的递归清单为空；
- 来源与禁止来源确认；
- Codex 生成后完整文件清单、大小和 SHA-256；
- `.pbip`、JSON、PBIR 引用和 TMDL 的离线语法/结构检查结果；
- Report `byPath` 解析到当前试验的 SemanticModel，而非 V0 或其他运行目录；
- Git 状态及仅包含当前试验生成物的预打开快照；
- Desktop 进程未运行的检查结果；
- `PREOPEN_MANIFEST.json` 和 `PREOPEN_VALIDATION.md`。

任一项缺失即不得进入 Desktop 阶段。

## 9. Desktop 与持久化验收

每组试验依次执行：

1. 人工从目标 `.pbip` 直接打开，不先创建任何 Desktop 项目。
2. 记录是否出现阻塞错误、修复警告、升级提示或需要人工选择的初始化动作。
3. 在尚未保存时采集磁盘清单，与 Codex 生成态比较。
4. 若项目可用，人工显式保存并关闭；记录关闭时是否再次提示保存。
5. 采集首存态清单和 SHA-256，并对项目结构、语义和字节差异分别分类。
6. 从同一 `.pbip` 重开；确认无阻塞错误，唯一 `Overview` 页面和语义模型可识别。
7. 在可用时通过 MCP 建立新连接，执行只读模型回读；不以 MCP 成功替代 Desktop 打开证据。
8. 再次关闭并确认 Git/磁盘状态稳定。

## 10. 差异分类

Desktop 首开或保存后的每个变化必须标记为以下一种：

- `CACHE_LOCAL`：仅 `.pbi/` 等本机缓存，排除出正式项目。
- `SERIALIZATION_EQUIVALENT`：等价序列化或换行变化。
- `DEFAULT_ENRICHMENT`：增加非必需默认属性或元数据。
- `VERSION_UPGRADE`：Schema/版本声明升级，结构仍等价。
- `STRUCTURAL_REQUIRED`：新增或修复项目成立所必需的文件、引用或对象。
- `SEMANTIC_CHANGE`：模型、页面或绑定语义改变。
- `UNKNOWN`：尚不能解释；在归因前不得给出最终结论。

## 11. 失败归因

每个失败先归入以下类别，再决定是否影响“种子必要性”：

| 代码 | 类别 | 例子 | 对结论的默认影响 |
| --- | --- | --- | --- |
| `GEN` | Codex 生成缺陷 | JSON 拼写、相对路径、标识符不一致 | 允许在新 attempt 修正；重复缺陷才说明当前生成方案不可靠。 |
| `SPEC` | 公开规范缺口或版本漂移 | 声明的 Schema 不可得、文档与 Desktop 不一致 | 可能支持“首次补写”或“仍需种子”，需看 Desktop 是否能无人工建壳恢复。 |
| `DESKTOP` | Desktop 兼容或持久化行为 | 阻塞打开、自动修复、必要结构补写 | 直接参与三级结论。 |
| `PATH` | 名称、路径、编码或长度问题 | Unicode/空格路径失败 | 形成适用范围限制；若受支持路径的两组试验成功，不单独证明需要种子。 |
| `MCP` | MCP 连接或回读问题 | 无本地实例、工具错误 | 不直接证明种子必要；Desktop 主证据可继续评估。 |
| `ENV` | 环境问题 | Desktop 版本变化、权限、进程残留 | 标记环境阻塞，修复环境后新 attempt 重试。 |
| `HUMAN` | 人工步骤偏差 | 打错项目、误点另存为 | 本次无效，保留记录后重做。 |
| `PROVENANCE` | 来源污染 | 读取或复制既有工程壳 | 本次无效，不能用于结论。 |

同一失败不得同时用多个模糊标签掩盖主因；可记录一个主因和若干促成因素，并附直接证据。

## 12. 最终结论规则

### 完全零种子

两组有效试验均满足：

- 空目录与来源证据完整；
- Codex 首次打开前生成全部最小项目文件；
- Desktop 直接打开，无阻塞错误、修复警告或人工建壳动作；
- 首开/首存没有 `STRUCTURAL_REQUIRED` 或无法解释的 `SEMANTIC_CHANGE`；
- 显式保存、关闭和重开均成功；
- 项目引用、唯一页面和模型在重开后仍可识别；
- 两组结果在不同名称和路径下可重复。

### Desktop 首次补写

两组有效试验都无需人工创建或另存为项目壳，且最终可稳定重开，但至少一组必须依赖 Desktop 的 `STRUCTURAL_REQUIRED` 补写、非阻塞修复或首次初始化。结论必须列出 Desktop 补写的精确文件与语义。

### 仍需人工种子

在排除 `ENV`、`HUMAN`、`MCP` 和单纯 `PATH` 问题后，至少两次独立、合规生成尝试仍无法让 Desktop 直接打开或稳定重开；继续成功必须依赖人工创建/保存的工程壳。不得仅因一个 Codex 拼写错误或一次环境故障下此结论。

### 无法判定

证据受污染、环境不稳定、两组结果冲突且未归因，或公开规范缺口使关键差异无法分类时，结论为“无法判定”，而不是强行归入三级之一。

## 13. 范围外

- Power BI Service 发布、共享、刷新计划和权限。
- 复刻 V0 完整业务模型、DAX、六视觉对象和交互验收。
- 跨机器免配置迁移。
- 性能、RLS、增量刷新、计算组、自定义视觉对象和多页面。
- 把零种子解释为零人工、零确认或零 Desktop 验证。
