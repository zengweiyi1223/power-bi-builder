# XHS 图文底稿：把 AI 开发从聊天变成项目闭环

- 状态：`Draft for Human Review`
- 对应方法：`Playbook v1.0.1-candidate`
- 用途：以人类易读方式检查 Playbook 是否清晰；不替代正式规范
- 建议形式：12 张知识卡片 + 一段正文
- 受众：使用 AI 做项目、但不希望被复杂工程流程拖累的个人或小团队
- 已选视觉方向：`B｜温暖项目手帐风`
- 封面英文眉题：`AI-native workflow`

## 定位与表达原则

这套方法本质上是：**以项目管理和项目治理为骨架，为 Human–AI 协作重新设计的轻量开发流程**。它覆盖目标、范围、责任、计划、质量、风险、变更、版本、交付和复盘，但不等同于完整企业 PMBOK，也不是一套提示词技巧。

正式制图时：

- 中文作为主称，英文术语只在首次出现时辅助标注；
- 每张卡片只保留一个结论、一个结构和少量关键词；
- 本底稿中的解释性段落进入发布正文，不全部塞进图片；
- 单卡正文建议控制在约 40～80 个汉字，流程标签另计；
- 视觉吸引力不能牺牲准确性，图卡不新增正式 Playbook 没有的规则。

## 一、标题候选

主标题：**我用几轮真实项目，把 AI 开发整理成了一套闭环流程**

备选：

- AI 会写代码，不等于项目能交付
- AI 时代的轻量项目管理：从想法到可验证交付
- 一套适合人与 AI 协作的可裁剪开发流程
- 不靠聊天记忆：我的 Human–AI 项目闭环

### 第 1 张｜封面

英文眉题：`AI-native workflow`

大标题：

> 把 AI 开发从聊天变成项目闭环

副标题：

> 一套适合 Human–AI 协作的轻量项目管理方法

视觉建议：奶油纸张、深蓝、陶土橙、低饱和鼠尾草绿；一条从“模糊想法”通向“可验证交付”的手绘主路径；避免可爱贴纸和过多小字。

### 第 2 张｜为什么需要 Playbook

大标题：**AI 能快速产出，但项目仍可能失控**

核心内容：

- 需求在对话中不断变化，却没有冻结；
- AI 自报完成，但缺少独立验证；
- 文件、版本、证据和回滚点找不到；
- 新对话依赖旧聊天记忆，恢复成本很高；
- 为了“不遗漏”又可能走向规则过重。

收口句：

> 真正要解决的不是“让 AI 多写一点”，而是让项目可验证、可停止、可恢复、可交付。

视觉建议：左侧“快但失控”，右侧“受控闭环”对比。

### 第 3 张｜Playbook 的五层结构

大标题：**本质上，是五层轻量项目管理系统**

```text
通用开发生命周期
+ 人机协作责任模型
+ 可裁剪阶段模块
+ 每阶段记录模板
+ Evidence Gate 证据闸门
```

说明：

- 生命周期回答“项目走到哪里”；
- 责任模型回答“谁决定、谁执行”；
- 裁剪回答“这个项目需要多少流程”；
- 模板回答“事实记录在哪里”；
- Evidence Gate 回答“凭什么进入下一步”。

它把传统项目管理中的目标、范围、责任、计划、质量、风险、变更和交接，转换成适合人与 AI 共同执行的最小控制结构。

视觉建议：五层同心圆或五块拼图。

### 第 4 张｜先识别项目，再裁剪流程

大标题：**不是所有项目都需要同样重的流程**

六种基础画像：

```text
实验研究｜文档内容｜数据分析
组件自动化｜交互应用｜生产服务
```

八类风险修饰器：

```text
UI｜数据｜外部系统｜部署
运维｜安全｜多人协作｜高代价风险
```

原则：

- 阶段可以合并，但不能静默消失；
- 不适用要说明理由；
- 风险只能增强流程；
- Contract 扩展后重新裁剪，不被最初画像绑住。

视觉建议：基础画像作为底盘，风险修饰器像可插拔模块。

### 第 5 张｜一条完整生命周期

大标题：**从模糊目标到正式交接，只保留一条主流程**

```text
项目画像与裁剪
→ 目标与问题澄清
→ 需求和验收契约
→ 产品/技术/体验设计
→ 任务计划与环境准备
→ 分阶段实现与验证
→ 集成验收
→ 发布或受控交付
→ 运行与观察（按条件）
→ 交接、关闭与复盘
```

说明：小项目可以合并阶段，生产服务会启用更多运行和恢复要求。

视觉建议：一条横向时间轴，实施阶段用循环符号表示。

### 第 6 张｜Human 与 AI 怎样分工

大标题：**AI 可以连续执行，但不能代替人做关键决定**

Human 负责：

- 为什么做、为谁做；
- 重要方案取舍和风险接受；
- 账号、费用、外部发布和不可逆操作；
- 主观验收和最终授权。

AI 负责：

- 澄清、起草和方案比较；
- 已冻结范围内的实现；
- 自动验证、差异分析和证据整理；
- 发现冲突时停止并升级。

原则：Human Gate 必须有明确批准人，AI 不能依据沉默自行通过。

视觉建议：两列职责表，中间用 Shared 区域连接。

### 第 7 张｜先冻结目标，再选择方案

大标题：**需求、验收、安全和方案要在实现前对齐**

Contract 至少回答：

```text
为什么做｜做什么｜不做什么
如何验收｜何时停止｜谁来批准
允许改哪里｜安全和权限边界
```

保留三种口径：原始表达、当前批准 Contract、未来 Backlog。

重要方案先比较候选、成本、风险和验证方法。遇到常见产品、新技术路线或重要依赖时，可以进行限时 Reference Scan：参考 GitHub 和官方实现，但不因为别人功能多就扩大自己的范围。

视觉建议：漏斗图——原始想法经过澄清、参考、比较后形成冻结 Contract。

### 第 8 张｜任务怎样拆、先做什么

大标题：**任务必须小到能够独立判断成败**

每个增量记录：

```text
依赖｜责任｜完成定义｜验证
证据｜风险｜停止条件｜checkpoint
```

默认顺序不是机械“从易到难”：

1. 先处理权限、环境和不可逆风险；
2. 尽早验证最贵、最不确定的假设；
3. 建立最薄端到端闭环；
4. 再从低耦合扩展到复杂集成。

视觉建议：风险优先 → 最薄闭环 → 增量扩展的三段阶梯。

### 第 9 张｜Evidence Gate：怎样证明真的完成

大标题：**每完成一个增量，立即验证，不等全部做完**

```text
Implement
→ 自动验证
→ 必要的人工验证
→ 保存证据
→ 判定与归因
→ Git checkpoint
```

关键原则：

- 关键结论不能只靠生成链路自证；
- 使用独立 Oracle、不变量、静态检查、真实回读或人工量表；
- Blocking Failure 停止依赖任务；Warning 不等于失败；
- 验证失败、环境失败、权限阻塞和证据缺口分别归因；
- Git 回滚点以阶段为主，高风险动作前额外建立。

视觉建议：闭环圆环，中间写“Evidence”。

### 第 10 张｜验收、交付、运维与 Handoff

大标题：**代码写完，不等于项目已经交付**

必须区分：

```text
已构建 ≠ 已发布 ≠ 已可用
```

集成验收检查各部分组合后是否满足 Contract；外部写入前核对目标、版本、权限、影响和回滚。长期运行项目再增加健康信号、监控、升级和恢复。

最终 Handoff 应包含：

- 功能结果、符合度和证据完整度；
- 交付入口与复核方法；
- Decision、Deviation、限制和残余风险；
- checkpoint、恢复方式和下一项唯一动作。

视觉建议：Build → Publish → Available 三个不同状态，最后汇入 Handoff。

### 第 11 张｜README、AGENTS 与记录体系

大标题：**让人和 AI 都能快速进入项目**

入口分工：

- README：人类优先入口，说明目的、状态、使用和 Artifact Map；
- AGENTS：条件式 AI 自动入口，只放阅读顺序、权限边界和已验证命令；
- REQUIREMENTS：冻结范围和验收；
- VALIDATION：唯一滚动状态与证据；
- HANDOFF：最终稳定摘要；
- PROJECT：画像、责任、裁剪和导航。

技术设计、交付计划、UAT、发布和 Runbook 按条件启用。文件可以合并，但同一状态不能有两个权威来源。

视觉建议：人从 README 进入，AI 从 AGENTS 进入，最终汇合到同一组权威记录。

### 第 12 张｜跨对话协作与轻量治理

大标题：**默认让人交接，自动编排按收益选择**

两种模式：

- Human Relay：执行对话更新仓库并返回短摘要，人类审核后交棒；
- Automatic Orchestration：自动派发、等待和回读，省操作但更耗 Token。

最小转移包：

```text
仓库与路径｜固定基线｜分支与 HEAD
当前 Gate｜权威文档｜验证结果
Decision/Deviation/Blocker｜下一项唯一动作
```

规则治理：只有重复出现或高损失的问题才优先进入 Required；其余优先使用 Guidance、模板、自动检查或案例。规则不是越多越好。

收口句：

> Playbook 的价值不是让每个项目写更多文档，而是用最小治理成本，避免关键遗漏。

视觉建议：左侧 Human Relay、右侧自动编排，底部统一进入仓库证据。

## 三、XHS 正文草稿

以前我很容易把“AI 已经生成了代码”理解成“项目快完成了”。但几轮真实实验后发现，真正困难的不是生成，而是需求不断漂移、验证由同一条链路自证、新对话无法恢复、版本和证据找不到，以及为了避免遗漏又写出一套过重流程。

所以我把实际过程整理成一套可裁剪的 Human–AI 项目 Playbook：先识别项目类型和风险，冻结目标、范围、验收和权限，再比较方案、拆分任务；每完成一个小增量就立即验证、归因和建立 Git checkpoint，最后完成集成验收、受控交付、必要运维与 Handoff。

这套方法最核心的不是模板，而是三个原则：

1. Human 负责目标、取舍、风险和最终授权，AI 负责已冻结范围内的分析、实现、验证和证据；
2. 关键结论不能由生成结果的同一条链路自证；
3. 流程必须按项目风险裁剪，规则不是越多越好。

我也把跨对话协作分成两种模式。默认由 Human 作为交接棒，只转移固定基线、当前 Gate、验证结果和下一动作；需要无人值守时再使用自动派发和回读。详细事实始终以仓库文档、代码、测试和 Git 为准，不依赖聊天记忆。

这套方法已经从 Power BI 实验扩展到非 Power BI 数据工具，但完整生产运维、多团队、高风险监管项目、开源调研的实际提效和 Skill 封装仍需要继续验证。它不是“万能标准”，而是一套可以从小项目开始、随风险增加的控制骨架。
