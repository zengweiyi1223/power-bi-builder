- 唯一发布定稿：[图文定稿](xhs-v1.0.1/FINAL.md)；冻结核查：[核查记录](xhs-v1.0.1/FREEZE.md)
- 对应方法：`Playbook v1.0.1-candidate`

## 1. 定位与表达原则

这套方法本质上是：**以项目管理和项目治理为骨架，为 Human–AI 协作重新设计的轻量开发流程**。它覆盖目标、范围、责任、计划、质量、风险、变更、版本、交付、运行和复盘，但不等同于完整企业 PMBOK，也不是一套提示词技巧。

正式制图时遵守以下规则：

- 中文作为主称，英文术语只在首次出现时辅助标注；
- 全篇只使用一套六步主流程编号，页面编号、任务名和机制不再混用数字；
- 先展示主流程，再解释阶段内循环和贯穿支撑，不能把它们画成同级步骤；
- 每张图只有一个主结论和一个明确阅读方向；
- 正文承担边界、解释和限定，不把全部规范硬塞进图片；
- 视觉吸引力不能牺牲关系准确性，图卡不新增正式 Playbook 没有的规则；
- 图片负责方法地图和关键事实，Rule ID、完整术语定义和模板字段仍回到正式 Playbook。

## 2. 视觉与信息规范

### 2.1 视觉语言

- 暖白或浅米灰纯色背景，只保留极弱纸张质感；
- 深海军蓝作为正文，陶土橙用于关键动作，低饱和鼠尾草绿用于通过或完成状态；
- 不使用山景、树林、胶带、卡片堆叠、厚阴影和无语义图标；
- 页面只保留细线、箭头、编号和少量状态块；
- 信息区紧凑但不拥挤，避免巨型标题和大面积无效留白。

### 2.2 关系语言

- `1～6`：只表示完整生命周期；
- `任务 A / 任务 B`：表示增量任务，不再添加数字序号；
- 菱形或闸门：表示必须经过的判断或人工授权；
- 细横带：表示贯穿主流程的责任、文档、Git 和证据；
- 回环箭头：只表示反馈进入下一轮；
- 页面右上角的小型 `P1～P9`：仅表示阅读页码。

### 2.3 三层信息模型

第一层只讲六步主流程：

```text
1 明确为什么做
→ 2 冻结范围和完成标准
→ 3 设计方案并拆任务
→ 4 小步实现、边做边验
→ 5 验收、交付和运行
→ 6 总结经验、进入下一轮
```

第二层解释第 4 步内部的阶段循环：

```text
实现 → 自动验证 → 必要时人工确认 → 判定 → 保存证据和 Git 回滚点
```

第三层展示贯穿支撑：

```text
人与 AI 的责任
文档、Git 与证据
决策、偏差与问题记录
```

## 3. 扩展讲解主题（图片选材与正文素材）

### 主题 1｜封面主张

英文眉题：

> AI-native workflow

主标题：

> 把 AI 开发变成项目闭环

副标题：

> 一套适配不同项目的轻量开发与协作方法

底部六个短词形成克制的小回环：

```text
明确目标 → 冻结契约 → 设计拆分
→ 实现验证 → 验收交付 → 反馈更新 ↩
```

收口句：

> 先把目标说清楚，再让人与 AI 按证据逐步推进。

版式：极简封面。标题不超过页面上部四分之一；六个短词必须有连续箭头和回环关系，不画成六张独立卡片。

### 主题 2｜完整生命周期

标题：

> 一件事，怎样从想法走到下一轮？

六步主流程：

```text
1 明确为什么做
  目标、用户和成功结果

2 冻结范围和完成标准
  做什么、不做什么、怎样算通过

3 设计方案并拆任务
  先后顺序、风险和责任

4 小步实现，边做边验
  实现 → 验证 → 必要时人工确认 → 判定与回滚点

5 验收、交付和运行
  证明结果可用，并说明如何继续维护

6 总结经验，进入下一轮
  HANDOFF、项目反馈和方法更新
```

第 6 步使用一条清楚的回环箭头返回下一轮第 1 步。

底部三条贯穿支撑：

```text
人与 AI 的责任
文档、Git 与证据
决策、偏差与问题记录
```

版式：纵向单路径。主流程是唯一视觉主轴，三条支撑线只放在底部，不与六步争夺层级。

### 主题 3｜从想法到可执行方案

眉题：

> 真实案例｜本地库存查询 MVP

标题：

> 前三步，把模糊想法变成可执行契约

对应六步中的 `1～3`：

```text
1 为什么做
  快速查询不同地点的商品库存

2 冻结契约
  首版只做关键词查询
  “燕麦”返回两个地点
  非法参数稳定报错
  无结果显示空状态
  暂不做登录、云部署、CSV 和写操作

3 设计拆分
  SQLite + API + Vue
  任务 A：先完成数据与 API
  任务 B：再接入 Vue 查询页面
```

侧边小注：

- 保留原始想法、当前批准 Contract 和未来 Backlog 三种口径；
- Contract 同时冻结允许修改范围、权限和安全边界；
- 重要方案可先比较候选，必要时限时参考官方资料和 GitHub 开源项目，但不因此扩大自己的范围。
- 实施前检查环境、版本、权限、目标身份和回滚条件；必要能力缺失时停止，不静默切换路线。

底部接力条：

```text
输入｜模糊想法
产出｜REQUIREMENTS + TECH_DESIGN + DELIVERY_PLAN
下一关｜任务 A
```

### 主题 4｜阶段内怎样推进

标题：

> 第 4 步不是一直写，而是边做边验

任务推进：

```text
任务 A｜数据 + SQLite + API
21 项测试通过
        ↓
必要的人工确认（Human Gate）
确认后才能继续
        ↓
任务 B｜Vue 查询页面
累计 30 项测试通过
```

两个任务都执行同一个阶段循环：

```text
实现
→ 自动验证
→ 必要时人工确认
→ 保存证据
→ 判定通过或停止
→ 建立 Git checkpoint
```

真实问题示例：

> `vue-tsc` 与 TypeScript 版本不兼容，被归因为依赖环境问题，而不是业务逻辑失败。

独立验证说明：关键结论不能只依赖生成链路的成功声明；可使用独立 Oracle、不变量、静态检查、真实外部回读或人工量表。

底部接力条：

```text
输入｜冻结契约
产出｜可复核实现与证据
下一关｜最终验收
```

### 主题 5｜验收、交付和反馈

标题：

> 做完功能之后，还要把项目真正关上

对应六步中的 `5～6`：

```text
5 验收、交付和运行
  类型检查通过
  30 项自动测试通过
  生产构建通过
  真实 HTTP 验证通过
  桌面与窄屏浏览器检查通过
  合并 main 并保留恢复点

6 总结经验，进入下一轮
  形成 HANDOFF
  记录已完成与未完成范围
  记录分支、HEAD、验证结果和恢复方法
  将跨对话恢复经验反馈给 Playbook
```

状态必须区分：

```text
已构建 ≠ 已发布 ≠ 已可用
```

本案例没有部署到云端，因此云部署和生产运维明确标记为未执行，而不是被默认为完成。

底部接力条：

```text
输入｜候选结果
产出｜正式验收 + HANDOFF
下一轮｜项目反馈与方法更新
```

### 主题 6｜按项目风险裁剪

标题：

> 流程不是越完整越好，而是要按风险裁剪

六种基础画像：

```text
实验研究｜文档内容｜数据分析
组件自动化｜交互应用｜生产服务
```

八类风险修饰器：

```text
UI｜数据｜外部系统｜部署
运维｜安全｜多人协作｜高代价风险
```

裁剪原则：

- 小项目可以合并阶段，但不能让风险静默消失；
- 不适用项要说明原因；
- Contract 扩展后必须重新识别风险和裁剪流程；
- 风险只会增强控制，不会因为项目最初很小而被忽略；
- 通用 Core 保持稳定，Power BI、数据工具或 Web 应用的具体生命周期由领域 Adapter 补充。

参考调研是风险触发、限时执行的 Guidance：先冻结自己的问题，再筛选少量官方或开源实现，记录借鉴、拒绝、许可和安全风险，不直接运行来源不明的脚本。

### 主题 7｜人与 AI 分工和交接

标题：

> AI 可以连续执行，但不能代替人做关键决定

Human 负责：

```text
目标与原因｜方案取舍｜风险接受
账号和费用｜外部发布｜最终授权
```

AI 负责：

```text
澄清与比较｜任务实现｜自动验证
差异分析｜证据整理｜发现冲突时停止
```

Human Gate：未经指定人明确批准，不得进入后续依赖阶段；沉默不代表通过。

跨对话默认采用 `Human Relay`：执行对话更新仓库并返回短摘要，由人类审核后交棒。只有在免手操作收益明显高于 Token 和协调成本时，才使用自动派发、等待和回读。

最小转移包：

```text
仓库与路径｜固定基线｜分支与 HEAD
当前 Gate｜权威文档｜验证结果
Decision / Deviation / Blocker｜下一项唯一动作
```

### 主题 8｜文件怎样承载项目状态

标题：

> 对话负责讨论，仓库负责记住事实

入口与记录：

| 项目问题 | 权威记录 |
| --- | --- |
| 项目是什么、当前在哪里 | `README / PROJECT` |
| AI 先读什么、能做什么 | `AGENTS`（按条件启用） |
| 做什么、不做什么、如何验收 | `REQUIREMENTS` |
| 采用什么方案 | `TECH_DESIGN` |
| 如何拆分和推进 | `DELIVERY_PLAN` |
| 为什么改变或偏离 | `RECORDS` |
| 如何证明完成 | `VALIDATION` |
| 如何发布、运行和恢复 | `RELEASE_OPERATIONS` |
| 如何交给下一人或 AI | `HANDOFF` |
| 方法哪里需要更新 | `PLAYBOOK_FEEDBACK` |

文件结构同时区分：

```text
输入与 fixtures / seeds
工作副本与 runs
日志、输出与 evidence
```

记录分为三类：规范 `Normative`、固定基线 `Baseline`、执行事实 `Record`。物理文件可以合并，但同一种状态只能有一个权威来源；README 面向人类，AGENTS 只作为简短 AI 入口，不能复制整套 Playbook。

固定输入、可信基线、工作副本、正式证据和可重建临时文件必须分开；不得在已验证基线原件上直接实验。

### 主题 9｜可复用原则与治理

标题：

> 让人与 AI 把项目做完，而不只是把代码写出来

十个原则：

1. 先解释为什么做，再讨论做什么；
2. 方案冻结前，可以让多个 AI 参与比较；
3. 模糊目标必须转成范围和验收契约；
4. 先识别项目风险，再裁剪流程；
5. 任务按依赖、风险和不确定性排序，不机械追求从易到难；
6. 实现与验证组成阶段内循环；
7. 关键结论不能只由生成链路自己证明；
8. 高风险节点由人确认，低风险步骤尽量自动化；
9. Git、文档和证据必须能够恢复真实状态；
10. HANDOFF 不是终点，项目反馈必须进入下一轮。

异常归因：先写受影响的验收项、现象和影响，再记录事件类型/严重度；沿需求与方案、输入、实现/依赖/环境、权限、验证依据和记录等方向找证据。区分已确认、待验证和未知原因，记录下一动作；修复或恢复后重验受影响的关口。原因列表是排查线索，不是逐项打勾清单。

规则治理：

```text
Required｜必须遵守
Provisional｜必须测试，允许被证伪
Guidance｜建议采用，可说明理由后裁剪
```

遵守某条规则不等于证明它有效，因此实验反馈必须分开评价 `conformity` 和 `utility`。只有重复出现或可能造成高损失的问题才优先升级为 Required；其余优先使用 Guidance、模板、自动检查或案例。

统一执行状态：

```text
未开始｜进行中｜通过｜有限通过｜阻塞｜失败｜不适用
```

正式记录对应：`Not Started / In Progress / Passed / Passed with Limitations / Blocked / Failed / Not Applicable`。

收口句：

> 流程的目的不是增加文档，而是减少返工、失忆和不可解释的失败。

## 5. XHS 正文草稿

以前我很容易把“AI 已经生成了代码”理解成“项目快完成了”。但几轮真实实验后发现，真正困难的不是生成，而是需求不断漂移、验证由同一条链路自证、新对话无法恢复、版本和证据找不到，以及为了避免遗漏又写出一套过重流程。

所以我把实际过程整理成一套可裁剪的 Human–AI 项目 Playbook。主流程只有六步：先明确为什么做，冻结范围和完成标准，设计方案并拆分任务；再小步实现、边做边验，完成验收和交付，最后把经验反馈到下一轮。

跨对话协作默认采用 Human Relay：执行者把正式状态写回仓库并提交短摘要，由人核对后交棒；只有免手操作收益明显高于额外 Token 与协调成本时，才启用自动编排。

图中使用的库存查询工具不是虚构示例。它从一句模糊想法开始，先冻结首版只做关键词查询，再拆成数据与 API、Vue 页面两个任务。后端通过 21 项测试并经过人工确认后才进入前端；最终累计 30 项测试，并完成类型检查、构建、真实 HTTP 和浏览器验证。项目最后合并到 main、形成 HANDOFF，同时明确记录登录、云部署、CSV 和写操作仍未实现。

这套方法最核心的不是模板，而是三个原则：

1. Human 负责目标、取舍、风险和最终授权，AI 负责已冻结范围内的分析、实现、验证和证据；
2. 关键结论不能由生成结果的同一条链路自证；
3. 流程必须按项目风险裁剪，规则不是越多越好。

我也把跨对话协作分成两种模式。默认由 Human 作为交接棒，只转移固定基线、当前 Gate、验证结果和下一动作；需要无人值守时再使用自动派发和回读。详细事实始终以仓库文档、代码、测试和 Git 为准，不依赖聊天记忆。

这套方法已经从 Power BI 实验扩展到非 Power BI 数据工具，但完整生产运维、多团队、高风险监管项目、开源调研的实际提效和 Skill 封装仍需要继续验证。它不是“万能标准”，而是一套可以从小项目开始、随风险增加的控制骨架。

## 7. 发布前检查

- 是否能通过六张图理解从常见卡点、通用流程、风险裁剪、角色协作、落地动作到真实案例；
- 图片是否始终只使用同一套六步生命周期编号；
- 是否明确区分主流程、阶段内循环和贯穿支撑；
- 是否明确“按风险裁剪”，没有制造所有项目都要写全部文档的误解；
- 是否区分 Human Gate、自动验证和 AI 自报状态；
- 是否把 Reference Scan 表述为条件式，而不是无限调研；
- 是否区分已构建、已发布和已可用；
