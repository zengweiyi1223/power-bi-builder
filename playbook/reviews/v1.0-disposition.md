## 1. 审查口径

每项结论同时回答四个问题：

1. 实验是否遵守了它（Conformity）？
2. 它是否发现问题、减少遗漏或支持恢复（Utility）？
3. 证据能否跨出 Power BI，还是仍是单项目观察？
4. 应进入 Core、模板、Power BI adapter、专项指南，还是只保留为项目事实？

处置值使用 `Keep / Change / Add / Promote / Retire / Defer / Move`。高 Conformity 不自动等于高 Utility；单个非 Power BI 项目也不能证明适用于所有领域。

候选生命周期统一为：

```text
Profile & Tailor
→ Discover & Frame
→ Contract
→ Design
→ Plan & Prepare
→ [Implement → Verify → Human Gate → Decide → Checkpoint] × N
→ Integrated Acceptance
→ Release / Delivery
→ Operate / Observe
→ Handoff / Close / Learn
```

阶段可以合并，但不能丢失适用性理由、责任、输入、验证、记录、退出 Gate 和恢复条件。

### 多视角方案评审边界

“多个 AI 讨论”是一种可选实现，不是治理主体。触发时应尽量让不同评审者独立检查同一问题或承担不同视角，例如产品价值、技术可行性、安全、验证和反方挑战；最终记录分歧、证据和人类决定。重复询问多个 AI 得到相同答案，不能替代独立事实验证。

### 任务排序原则

v1.0 不使用简单的“先易后难”作为强制顺序。默认排序依据是：

1. 先处理会阻塞路线的权限、环境和不可逆风险；
2. 尽早验证代价最高或最不确定的关键假设；
3. 建立一个可运行、可验证的最小端到端闭环；
4. 再由低耦合、易归因的增量扩展到复杂集成；
5. 每个增量通过 Gate 后再进入依赖任务。

## 5. 记录与物理文件策略

### 5.1 最小逻辑记录

| 逻辑记录 | 要求 | 单一权威内容 |
| --- | --- | --- |
| PROJECT | Required | 项目入口、画像、修饰器、角色、阶段裁剪、Artifact Map |
| REQUIREMENTS | Required | 原因、目标、范围、非目标、验收、安全、Human Gate |
| VALIDATION | Required | 唯一滚动阶段状态、证据、异常、Gate 和 checkpoint |
| HANDOFF | Required | 最终交付入口、稳定结论、限制、恢复和后续边界 |
| RECORDS | Conditional | 重大 Decision 与 Deviation |

### 5.2 条件式逻辑记录

| 触发条件 | 逻辑记录 |
| --- | --- |
| 存在重要架构、接口、数据、安全或依赖取舍 | TECH_DESIGN / ADR |
| 多阶段、多依赖或多人协作 | DELIVERY_PLAN |
| 存在界面和关键交互 | UX_SPEC 或受控设计链接 |
| 需要正式用户验收 | UAT / REVIEW |
| 需要部署、迁移或外部发布 | RELEASE_PLAN / deployment evidence |
| 需要持续运行、监控或恢复 | RUNBOOK / incident records |
| 方法验证项目 | PLAYBOOK_FEEDBACK |

逻辑记录不等于独立文件。小项目可以合并，复杂项目可以拆分；同一动态状态只维护在一个权威位置。`PROJECT` 和 `HANDOFF` 只给稳定摘要，不复制 `VALIDATION` 的滚动明细。

### 5.3 推荐信息分区

v1.0 只要求以下信息可区分，不强制固定目录名：

- 根入口与治理记录；
- 产品/实现资产；
- 测试、fixture 与独立 Oracle；
- 正式证据和运行记录；
- 发布、运维和恢复资料；
- 可重建的生成物、缓存和临时文件。

画像指南可以分别给出单次实验、多实验集合、组件、应用和服务的示例树。根入口必须解释实际映射，避免仅凭目录名猜测。

## 6. Power BI 工具路线边界

v1.0 的 Power BI adapter 应增加能力路由，而不是把所有能力统称为“插件”：

| 工作对象 | 默认路线 | 当前证据状态 |
| --- | --- | --- |
| 本地文件、PBIP/PBIR/TMDL | 文件与代码工具 | V0/V1 observed |
| Power BI Desktop 内存模型与本地回读 | Desktop + 可选 Modeling MCP | 部分由 V0/V1 observed；对象级边界按 adapter 说明 |
| Power BI Service 中查看、编辑视觉对象、保存、发布和分享 | Power BI 浏览器插件 | 工具说明支持；本项目实验未验证 |
| REST API、后台集成或本地 Desktop 自动控制 | 单独选择并验证相应工具 | 不由浏览器插件自动覆盖 |

插件路线涉及租户、账号、workspace、权限、覆盖、分享或公开发布时，仍必须执行身份核对、Human Gate、外部回读和结果状态区分。案例研究只记录真实使用过的路线；未使用的插件不能写成实验成功经验。

## 7. 不进入通用 Core 的内容

- CRLF JSON 载体、SVG LF、5 MiB 阈值、Vanilla TypeScript、Edge/CDP、GitHub Pages 和 `ubuntu-latest`；
- Power BI Desktop、PBIR、TMDL、MCP 或浏览器插件的对象级操作；
- “所有项目使用同一目录树”“所有项目必须多个 AI 讨论”“所有任务机械地由易到难”；
- 未执行的公开环境降级回滚、未测试的效率计量、完整 PF-SVC 运维、多团队和高风险/监管场景结论。

这些内容分别保留在项目事实、模板提醒、Power BI adapter 或后续验证列表中。

## 9. v1.0 验收标准

- 所有 v0.2 Rule ID 均有明确处置，保留 ID 的规则可追溯；新增规则具有稳定 ID、等级和适用边界。
- 生命周期只有一条；Evidence Gate 是阶段内循环，不是并列流程。
- 六种画像、修饰器和 `Required / Conditional / Not Applicable + 理由` 可以驱动阶段裁剪。
- Requirements、Tech Design、Validation 三类记录的职责和触发条件明确。
- 根目录入口、Artifact Map、逻辑记录与物理文件映射可读；不要求唯一目录树。
- AI、Human、Shared、Automation 责任与 Review/Approve 控制可执行。
- 方案冻结前包含目标原因对齐；多 AI 仅为条件式 Guidance。
- 任务拆分、风险排序、原子验证和 checkpoint 能连成同一推进链。
- 每次新会话或恢复执行前能从唯一 Validation 控制状态确定允许范围、Blocker、下一 Gate 和 rollback point；缺失或冲突时停止。
